# AcmeCloud Monitoring Specification

## Objectives

The AcmeCloud monitoring platform provides visibility into the health,
availability, and resource utilization of the Kubernetes infrastructure
and application workloads.

## Infrastructure Monitoring

Monitor Amazon EKS worker nodes for:

- Node availability
- CPU utilization
- Memory utilization
- Filesystem utilization
- Network activity

## Kubernetes Monitoring

Monitor Kubernetes resources for:

- Pod health and status
- Container restart counts
- Deployment replica availability
- Container CPU utilization
- Container memory utilization
- Namespace health

## AcmeCloud Application Monitoring

Monitor workloads in the `acmecloud` namespace:

- acmecloud-web deployment
- acmecloud-app deployment
- Web pod availability
- Application pod availability
- CPU consumption
- Memory consumption
- Container restarts

## Metrics Collection

Prometheus collects metrics from:

- Kubernetes API components
- kube-state-metrics
- node-exporter
- kubelet and container metrics

## Visualization

Grafana uses Prometheus as its primary data source.

Dashboards will provide visibility into:

- Cluster health
- Node resource utilization
- Kubernetes workload health
- AcmeCloud application health

## Alerting

Initial alerting will cover:

- Kubernetes node unavailable
- Pod/container restart activity
- Deployment replicas unavailable
- High CPU utilization
- High memory utilization

Alertmanager manages alerts generated by Prometheus alerting rules.

## Implementation

AcmeCloud monitoring is deployed to Amazon EKS using the
`kube-prometheus-stack` Helm chart.

### Helm Release

- Release: `acmecloud-monitoring`
- Namespace: `monitoring`
- Chart: `kube-prometheus-stack`
- Chart version: `91.9.0`
- Application version: `v0.94.1`

The chart version is pinned to provide repeatable deployments.

### Amazon EKS Configuration

Because the Kubernetes control plane is managed by Amazon EKS, monitoring
for etcd, kube-controller-manager, and kube-scheduler is disabled.

kube-proxy remains monitored because it runs on the EKS worker nodes.

Validation confirmed 21 active Prometheus scrape targets and 21 healthy
targets.

### Monitoring Components

The monitoring namespace contains:

- Prometheus
- Grafana
- Alertmanager
- Prometheus Operator
- kube-state-metrics
- node-exporter

Grafana, Prometheus, and Alertmanager use ClusterIP services and are not
directly exposed to the public internet.

### Custom Alerting

Custom Prometheus rules are defined in:

    monitoring/alerts/acmecloud-alerts.yaml

The rules monitor:

- Kubernetes node availability
- High node CPU utilization
- High node memory utilization
- AcmeCloud container restarts
- Unavailable deployment replicas
- AcmeCloud pod readiness

All six custom alert rules were successfully loaded by Prometheus.

Prometheus successfully discovers the Alertmanager endpoint. Alertmanager
currently uses the default null receiver. External notification credentials
are intentionally not stored in the repository.

### Grafana Dashboard

The dashboard source is stored in:

    monitoring/dashboards/acmecloud-overview.json

The AcmeCloud dashboard contains ten panels covering pod availability,
deployment replicas, container restarts, active alerts, pod CPU and memory,
and EKS node CPU and memory utilization.

During deployment, the dashboard JSON is placed in a Kubernetes ConfigMap
with the label:

    grafana_dashboard=1

The Grafana dashboard sidecar automatically discovers the ConfigMap.

Grafana can be accessed securely using local port forwarding:

    kubectl -n monitoring port-forward \
      svc/acmecloud-monitoring-grafana 3000:80

### Repeatable Deployment

The AWS lab restore workflow automatically restores monitoring after the
EKS environment and AcmeCloud workloads are available.

The restore process includes:

1. Restore AWS networking and NAT.
2. Restore EKS and managed worker nodes.
3. Configure kubeconfig and wait for Ready nodes.
4. Install the AWS Load Balancer Controller.
5. Deploy the AcmeCloud application.
6. Create the ALB Ingress.
7. Validate the application endpoints.
8. Install kube-prometheus-stack.
9. Apply the AcmeCloud Prometheus alert rules.
10. Provision the AcmeCloud Grafana dashboard.

The monitoring deployment was tested for idempotency. Helm successfully
upgraded the existing release, while the custom PrometheusRule and Grafana
dashboard remained unchanged.

### Storage and Cost Control

Prometheus and Grafana currently use ephemeral storage for this portfolio
lab. Persistent monitoring storage can be introduced later for a
long-running production environment.

The monitoring stack is recreated when the AWS lab is restored and is
removed with the EKS environment during the cost-control shutdown.
