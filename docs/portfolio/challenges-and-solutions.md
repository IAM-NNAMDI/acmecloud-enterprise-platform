# AcmeCloud Enterprise Platform — Challenges and Solutions

Building the AcmeCloud Enterprise Platform involved troubleshooting real infrastructure, configuration-management, container, Kubernetes, CI/CD, observability, and AWS lifecycle issues.

This document records selected engineering challenges encountered during the project, their root causes, the solutions implemented, and the lessons learned. It demonstrates the troubleshooting and decision-making process behind the final platform rather than only presenting the finished architecture.

## Phase 1 — Terraform and AWS Infrastructure

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| Terraform failed with an `Invalid index` error while configuring private routing. | The configuration referenced `aws_nat_gateway.nat[0].id` when NAT Gateway creation was disabled, leaving the resource collection empty. | The routing logic was corrected so optional NAT infrastructure was handled conditionally rather than referenced unconditionally. | Terraform could evaluate the configuration without indexing a nonexistent NAT Gateway. Optional resources must be reflected consistently in dependent resources. |
| Terraform rejected the bastion CIDR configuration. | `bastion_allowed_cidr` still contained the placeholder `YOUR_PUBLIC_IP/32`, which failed variable validation. | The placeholder was replaced with a valid public IPv4 CIDR using `/32` for restricted administrative access. | Input validation caught an unsafe/incomplete deployment value before infrastructure creation. |
| EC2 creation failed with `InvalidAMIID.Malformed`. | The AMI variable still contained a placeholder rather than a valid AWS AMI ID. | A valid AMI for the target AWS region was supplied to Terraform. | Region-specific infrastructure identifiers must be validated before deployment. |
| Terraform module initialization failed for the ALB and database modules. | Module source paths did not match the case-sensitive directory names used in the repository. | The Terraform module paths were aligned with the actual `Alb` and `Database` directories. | Terraform successfully resolved the modules. Linux filesystem paths and Terraform module sources are case-sensitive. |
| Terraform destroy failed because RDS required a final snapshot identifier. | The database lifecycle had `skip_final_snapshot = false`, but no valid final snapshot identifier was available during destruction. | The RDS lifecycle configuration was reviewed and aligned with the intended lab teardown strategy. | Database destruction behavior must be designed deliberately; creation settings alone are not enough for repeatable infrastructure lifecycle management. |
| Terraform remote-state initialization reported an S3/DynamoDB checksum mismatch. | The S3 state object had previously been removed while DynamoDB still contained digest metadata for the old remote state. | The backend was investigated using AWS CLI checks against the S3 bucket, state key, and DynamoDB locking table so stale backend metadata could be identified and reconciled. | Remote Terraform state and its locking/checksum metadata must remain consistent. Manual state deletion can leave backend metadata that prevents subsequent initialization. |
| SSH from the bastion host reached the private EC2 instances but returned `Permission denied (publickey)`. | Network connectivity was working, but the target instances did not have the required private-key authentication path available from the bastion. | The issue was separated into networking versus authentication troubleshooting, and later configuration management moved toward AWS Systems Manager-based connectivity. | A successful TCP/SSH connection followed by a public-key rejection indicates an authentication problem rather than a routing or security-group failure. |
| Production-style AWS resources created unnecessary cost when the lab was not being used. | EKS, Application Load Balancers, NAT Gateway, and optional data services incur ongoing charges while provisioned. | Terraform feature flags and dedicated `aws-lab-shutdown.sh` / `aws-lab-restore.sh` lifecycle scripts were implemented so expensive runtime components could be disabled between demonstrations. | The final AWS audit confirmed that EKS, load balancers, available/pending NAT Gateways, RDS instances, and ElastiCache clusters were absent after shutdown. Cost management became part of the infrastructure design rather than an afterthought. |


## Phase 2 — Ansible Configuration Management

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| Ansible could reach the Ubuntu host but initially reported the RHEL application host as unreachable. | SSH public-key authentication to the RHEL node was failing, so Ansible could not establish its management connection. | SSH was tested independently of Ansible, `sshd` configuration and logs were inspected, and authentication problems were resolved before returning to the playbooks. | Troubleshooting the underlying transport separately prevented an SSH problem from being misdiagnosed as an Ansible problem. |
| RHEL `sshd` reported `bad ownership or modes for directory /root`. | OpenSSH security checks rejected key authentication because the ownership or permissions associated with the root SSH path were unsafe. | The filesystem permissions were corrected and SSH configuration was verified using `sshd -T` and service logs. A dedicated `ansible-user` was subsequently used for configuration management. | SSH key authentication depends on both key correctness and secure filesystem permissions. Server logs provided the decisive diagnostic evidence. |
| The dedicated `ansible-user` connected successfully but privilege escalation failed with `ansible-user is not in the sudoers file`. | The automation account had SSH access but did not yet have the privileges required for tasks using `become`. | Appropriate sudo privileges were configured for the Ansible automation account. | Successful SSH connectivity does not guarantee successful configuration management; remote identity and privilege escalation must be validated separately. |
| Apache automation failed when the wrong service name was used. | Ubuntu and RHEL use different Apache package/service conventions: Ubuntu uses `apache2`, while RHEL uses `httpd`. | The playbook/role implementation was aligned with the target operating system instead of assuming identical service names across distributions. | Configuration-management roles must account for operating-system-specific packages, services, and paths. |
| The SSH hardening handler failed because service `ssh` could not be found on RHEL. | The handler used the Ubuntu-style service name `ssh`, while RHEL manages the OpenSSH server through `sshd`. | The handler was corrected to restart/reload the RHEL `sshd` service. | Cross-platform automation should avoid hard-coded service assumptions or explicitly map service names by OS family. |
| Tomcat was installed but initially could not be reached on port `8080`, producing `No route to host`. | The RHEL firewall did not allow inbound TCP traffic on the Tomcat application port. | An `ansible.posix.firewalld` task was added to permanently and immediately allow `8080/tcp`. | Application troubleshooting must include the host firewall as well as the process, listening port, network route, and cloud security controls. |
| Tomcat validation initially reported `Unit tomcat.service could not be found`. | The custom systemd unit had not yet been deployed successfully when the service check was performed. | The Tomcat role was completed to deploy the systemd unit, reload systemd as required, and enable/start the service. | Service validation should follow successful configuration deployment; checking runtime state too early can obscure the actual configuration problem. |
| RHEL package-management tasks failed while the machine was unregistered. | The configured local DNF repositories referenced `file:///mnt/rhel9`, while the RHEL installation media was mounted at a different path. | The repository configuration and actual mounted-media location were inspected and aligned so package installation could use an accessible source. | Offline or unregistered RHEL systems require deliberate repository management; package failures are not necessarily caused by Ansible itself. |
| The `common` role was initially reported as not found. | `roles_path` in `ansible.cfg` did not match the reorganized project structure. | `roles_path` was corrected to point to the repository's `roles` directory. | Repository restructuring must be reflected in Ansible configuration and should be followed by syntax and role-resolution validation. |
| Static inventory was useful for the local lab but unsuitable for automatically changing AWS instances. | EC2 instances created by Auto Scaling and Terraform can receive different instance IDs and addresses over their lifecycle. | The project migrated to the `amazon.aws.aws_ec2` dynamic inventory plugin, grouping AWS instances by tags into `web`, `app`, and `bastion` groups. | Dynamic inventory removed hard-coded AWS host addressing and aligned configuration management with elastic infrastructure. |
| Direct SSH management of private AWS instances increased key-distribution and network-access complexity. | Private application instances required a secure management path without exposing SSH or distributing private keys through the environment. | AWS Systems Manager connectivity and EC2 IAM permissions were incorporated into the AWS configuration-management design. | Using AWS-native management channels reduced dependence on inbound SSH and improved the security model for private instances. |


## Phase 3 — AWS Monitoring and CloudWatch

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| Default EC2 monitoring did not provide the operating-system-level visibility required for the web and application servers. | Standard EC2 metrics focus primarily on AWS infrastructure and do not natively provide detailed guest OS metrics such as memory and filesystem utilization. | The Amazon CloudWatch Agent was installed and configured through Ansible to collect memory, disk, and swap metrics from the EC2 instances under the `AcmeCloud/EC2` namespace. | Monitoring configuration became repeatable through configuration management, and the project gained host-level telemetry beyond the standard EC2 metric set. |
| Monitoring configuration needed to remain consistent across dynamically discovered AWS instances. | Manually configuring the CloudWatch Agent on individual instances would not scale with the Terraform/Auto Scaling and dynamic-inventory model. | CloudWatch Agent installation and configuration were incorporated into the reusable Ansible monitoring role and applied to the AWS-managed hosts. | Observability configuration became part of automated server provisioning rather than a manual post-deployment task. |

## Phase 4 — Docker and Amazon ECR

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| The original EC2-hosted web and application tiers needed a portable runtime model before moving to Kubernetes. | Apache/Nginx and Tomcat configuration tied directly to individual servers would make the next orchestration phase harder to reproduce consistently. | The web and application tiers were containerized separately, using Nginx for the web/reverse-proxy tier and Tomcat 10 for the application tier. Docker Compose provided a local two-service integration environment. | The same application components could be built as images and later deployed to Amazon EKS, creating a consistent path from local container testing to Kubernetes. |
| The application tier needed to remain private while still being reachable by the web tier. | Publishing both containers directly to the host would bypass the intended layered architecture. | Both services were placed on a Docker bridge network. Only the Nginx web tier was published externally, while Tomcat remained internally accessible on port `8080`. | Container networking preserved the web-to-application traffic pattern that would later be reproduced with Kubernetes Services. |
| The web container could start before the application container was actually ready to serve requests. | Container startup order alone does not guarantee application readiness. | A health check was added to the application container, and Docker Compose was configured so the web service depended on the application becoming healthy. | Service orchestration should use health/readiness signals rather than assuming that a started process is ready for traffic. |
| Container images required a secure AWS registry for the EKS deployment phase. | Locally built images were not suitable for repeatable deployment to distributed Kubernetes worker nodes. | Private Amazon ECR repositories were created for `acmecloud-web` and `acmecloud-app`, with image scanning on push and immutable tags enabled. | ECR provided a controlled source of deployable images and prevented existing release tags from being overwritten. |
| Docker BuildKit-generated provenance metadata caused compatibility issues with the ECR image-manifest workflow used during the project. | The generated image metadata/manifest format did not match the format expected by the release workflow at that stage. | BuildKit provenance generation was disabled for the affected image builds before publishing them to ECR. | The images were successfully published and consumed from ECR. Container build metadata and registry manifest compatibility must be considered as part of the delivery pipeline. |
| Mutable image tags would make it difficult to determine exactly which source revision was running in production. | Reusing tags such as `latest` breaks the direct relationship between Git history, registry artifacts, and deployed workloads. | Production images were tagged using the first 12 characters of the Git commit SHA, with the same release identifier applied to both web and application images. | The final integrated release `536b0e8455a0` could be traced from Git through ECR to the Kubernetes deployment, enabling deterministic deployment and rollback. |


## Phase 5 — Kubernetes and Amazon EKS

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| One Kubernetes worker remained in `NotReady` state during the initial cluster lab. | The worker's hostname/node configuration did not correctly identify the node after provisioning. | The hostname was corrected with `hostnamectl`, the kubelet was restarted, and the node IP configuration was verified. | The worker returned to `Ready` state. Kubernetes node problems should be investigated from both the control-plane view and the node's kubelet/OS configuration. |
| The containerized application needed to move from Docker Compose to a resilient Kubernetes deployment model. | Docker Compose provided local orchestration but did not provide distributed scheduling, replica management, Kubernetes service discovery, or managed AWS integration. | Separate Kubernetes Deployments and ClusterIP Services were created for the Nginx web tier and Tomcat application tier, with two replicas of each workload. | The final EKS environment ran 2/2 web and 2/2 application replicas distributed across worker nodes. |
| Private ECR images needed to be pulled securely by EKS worker nodes. | Kubernetes workers require AWS authorization to retrieve private registry images. Manually maintained registry credentials would introduce unnecessary secret-management overhead. | EKS worker-node IAM permissions were used to authorize image pulls directly from private Amazon ECR repositories. | Production images were successfully pulled without manually managed ECR image-pull secrets. |
| The Kubernetes application needed public HTTP ingress without exposing individual pods or ClusterIP Services. | Kubernetes ClusterIP Services are intentionally private and cannot directly serve internet traffic. | The AWS Load Balancer Controller was integrated with EKS, and a Kubernetes Ingress resource was configured to provision an internet-facing Application Load Balancer using IP target mode. | The ALB routed traffic to the web tier, and both `/` and `/app/` returned HTTP 200 during production validation. |
| The web tier needed to reach Tomcat without exposing the application tier publicly. | Direct public access to Tomcat would bypass the intended layered application architecture. | `acmecloud-app` remained a ClusterIP Service, while Nginx routed application requests internally through Kubernetes service discovery/DNS. | `/app/` successfully followed the request path from ALB → Ingress → Nginx → Kubernetes Service → Tomcat. |
| Production manifests needed stronger container-level security controls. | Default container execution settings did not explicitly enforce least privilege. | Both workloads were configured for numeric non-root users, `runAsNonRoot: true`, `allowPrivilegeEscalation: false`, dropped Linux capabilities, and the `RuntimeDefault` seccomp profile. | The rendered manifests demonstrated explicit workload hardening rather than relying on container-runtime defaults. |
| A deliberately invalid container release caused replacement pods to enter `ErrImagePull`. | The resilience test intentionally referenced nonexistent ECR image tags to simulate a failed deployment. | Existing healthy replicas were allowed to remain available while the failed rollout was detected, after which the previous known-good web and application images were restored. | Both deployments returned to healthy state. The test demonstrated why rolling updates and deterministic rollback are important for service availability. |
| The base Kubernetes manifests required a release mechanism that would not permanently store a historical production image tag. | Hard-coding a previous production SHA into the base deployment manifests could accidentally redeploy an outdated release. | The base manifests use a `RELEASE_TAG` placeholder, while Kustomize injects the selected immutable image release during deployment. | Release selection became explicit and traceable while the reusable base manifests remained independent of a particular historical release. |
| Final repository validation revealed that `ingress.yaml` existed but was not included in the Kustomize resource list. | `kubernetes/eks/kustomization.yaml` referenced the namespace, Services, and Deployments but omitted the existing Ingress manifest. | `ingress.yaml` was added to the Kustomize `resources` list and the rendered output was regenerated. | `kubectl kustomize kubernetes/eks` successfully rendered six resource types: Namespace, two Services, two Deployments, and Ingress. The fix was isolated in commit `c3e61ca`. |


## Phase 6 — Prometheus and Grafana Observability

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| EC2-level CloudWatch monitoring did not provide sufficient visibility into Kubernetes workloads. | Host-level infrastructure metrics alone could not show pod readiness, deployment availability, container restarts, or Kubernetes object state. | `kube-prometheus-stack` was introduced to provide Prometheus, Grafana, Alertmanager, kube-state-metrics, and node-exporter monitoring for the EKS environment. | Observability expanded from infrastructure-level monitoring to Kubernetes node, pod, container, and workload visibility. |
| Raw metrics were available but needed to be presented in a form useful for operational troubleshooting. | Querying individual Prometheus metrics manually is inefficient during incident investigation and demonstrations. | A dedicated AcmeCloud Grafana dashboard was created with panels for ready pods, unavailable replicas, container restarts, active alerts, deployment replicas, pod CPU/memory, and EKS node utilization. | The dashboard provided a consolidated operational view of application and cluster health. |
| Monitoring needed to detect important conditions proactively rather than relying only on dashboard inspection. | Dashboards are useful for investigation but do not automatically identify conditions requiring attention. | Custom Prometheus rules were created for node unavailability, high CPU, high memory, container restarts, unavailable deployment replicas, and pods remaining not ready. | Alert rules converted important platform-health conditions into actionable signals processed by Alertmanager. |
| Exposing Grafana, Prometheus, and Alertmanager publicly would create unnecessary attack surface and additional AWS load-balancer cost. | Public Services or Ingress resources would make administrative monitoring endpoints internet-accessible and could provision additional chargeable infrastructure. | Monitoring services remained private using ClusterIP Services, with administrative access available through Kubernetes port forwarding when required. | Operational tooling remained accessible for administration without creating unnecessary public endpoints or additional load balancers. |

## Phase 7 — GitHub Actions CI/CD

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| CI/CD required AWS access to publish images and deploy workloads without storing long-lived cloud credentials in GitHub. | Static AWS access keys create secret-rotation overhead and increase the impact of credential exposure. | GitHub Actions OIDC federation was configured with a dedicated AWS IAM role, allowing workflows to request short-lived AWS credentials. | The workflow uses `id-token: write` and assumes the dedicated `acmecloud-production-github-actions` role instead of storing long-lived AWS access keys. |
| The pipeline needed to prevent invalid repository, Docker, Kubernetes, or vulnerable container changes from progressing directly toward deployment. | A build-and-deploy-only workflow would detect many problems too late in the release process. | Separate validation stages were introduced for repository checks, Docker builds, Kubernetes manifests, and Trivy HIGH/CRITICAL container vulnerability scanning before publication/deployment stages. | CI/CD became a quality and security gate rather than only a deployment mechanism. |
| Production releases needed a deterministic relationship between source code and deployed container images. | Mutable tags make it difficult to identify exactly which Git revision produced a running workload. | The workflow derives the production image tag from the first 12 characters of `GITHUB_SHA` and publishes matching web and application releases to ECR. | Git commit, ECR artifacts, Kustomize rendering, and Kubernetes deployment share a traceable immutable release identifier. |
| Automatic deployment on every repository push would be inappropriate for the production-style EKS environment and could create unnecessary AWS activity. | Repository validation and production deployment have different risk and cost profiles. | EKS deployment was gated so the production deployment job requires the explicit deployment path configured in the workflow rather than executing indiscriminately for every change. | Validation can run independently while production deployment remains a deliberate operation. |
| A successful `kubectl apply` does not prove that the new application version became healthy. | Kubernetes accepts desired state before replacement pods necessarily become ready. | The deployment job performs rollout-status verification for both the application and web Deployments after applying the rendered release. | Deployment success is based on workload rollout health rather than only successful manifest submission. |
| A failed rollout needed to restore the exact previously running release rather than guess a fallback image tag. | Rolling back to a mutable or assumed tag could restore the wrong application version. | Before deployment, the workflow records the currently running web and application image references. If rollout verification fails, those exact previous images are restored with `kubectl set image`, followed by rollout verification. | Rollback became deterministic and tied to the actual pre-deployment state. The mechanism was tested with deliberately invalid ECR image references. |
| CI/CD permissions needed to remain narrower than full infrastructure-administration permissions. | Giving the deployment workflow broad AWS/Kubernetes administrative access would violate least-privilege principles. | A dedicated GitHub Actions IAM role was created for the required ECR/EKS operations, while Kubernetes deployment authorization was scoped to the `acmecloud` namespace. | Application delivery permissions remained separated from general platform-administration responsibilities. |


## Phase 8 — Production Integration, Resilience and Cost Control

| Challenge | Root Cause | Solution Implemented | Validation / Lesson Learned |
|---|---|---|---|
| Components that worked independently still needed to operate as one integrated production-style platform. | Terraform, Ansible, Docker/ECR, Kubernetes, observability, and CI/CD had been developed in separate phases with different validation methods. | A final integration phase connected infrastructure provisioning, configuration management, immutable container releases, EKS deployment, ingress, observability, CI/CD, security, and lifecycle automation. | End-to-end validation confirmed that the individual DevOps components formed a coherent delivery and operations platform rather than a collection of isolated labs. |
| The final production release needed to remain consistent across source control, container images, and Kubernetes workloads. | Different release identifiers across components would make troubleshooting and rollback difficult. | The same immutable Git-SHA-derived release identifier was used for both application images and injected into Kubernetes through Kustomize. | Release `536b0e8455a0` provided a traceable path from source revision to ECR artifacts and the validated EKS deployment. |
| The production request path needed to be validated end to end rather than testing individual components only. | Healthy pods or a provisioned ALB do not independently prove that users can successfully reach the complete application path. | Validation covered ALB target health, the Nginx web endpoint, internal application routing, Kubernetes Services, and the Tomcat application endpoint. | Both `/` and `/app/` returned HTTP 200 during final integrated validation. |
| Deployment resilience needed to be demonstrated rather than assumed from Kubernetes rolling-update behavior. | A deployment configuration may appear correct but still fail operationally when a new image cannot start. | A controlled failure was introduced using invalid ECR image references. Rollout behavior was observed and the previous known-good images were restored. | Existing healthy replicas remained available while replacement pods failed with `ErrImagePull`, and both workloads recovered after rollback. |
| Production validation required observability across both infrastructure and Kubernetes workloads. | Application availability alone would not demonstrate the health of nodes, pods, deployments, containers, and monitoring components. | CloudWatch remained part of the AWS/EC2 monitoring path while Prometheus, Grafana, Alertmanager, kube-state-metrics, node-exporter, dashboards, and custom alert rules covered the EKS environment. | Final validation confirmed the Kubernetes monitoring stack was operational and the custom AcmeCloud alert rules were loaded. |
| Production-style AWS infrastructure was too expensive to leave running continuously for a portfolio lab. | EKS worker nodes, Application Load Balancers, NAT Gateway, and optional data services can continue generating charges when no demonstration is taking place. | Explicit Terraform feature flags and `aws-lab-shutdown.sh` / `aws-lab-restore.sh` scripts were incorporated into the operational lifecycle. Restore operations require an explicit immutable release and verify its ECR availability before runtime infrastructure is restored. | After final validation, chargeable runtime components were shut down. A read-only AWS audit returned no EKS clusters, load balancers, available/pending NAT Gateways, RDS instances, or ElastiCache clusters. |
| The completed repository needed to demonstrate implementation evidence without recreating expensive infrastructure purely for screenshots. | Historical AWS resources had already been intentionally destroyed for cost control, so recreating them only to produce portfolio images would contradict the project's lifecycle strategy. | Reproducible evidence was collected from Terraform validation, Ansible configuration, current ECR metadata, Kubernetes rendering/security configuration, CI/CD source, monitoring configuration, and the final AWS cost-control audit. | The repository now contains five architecture diagrams and fifteen categorized evidence screenshots without recreating unnecessary chargeable AWS resources. |

## Key Engineering Lessons

The AcmeCloud lifecycle reinforced several engineering principles:

- Troubleshoot from the lowest failing layer upward: connectivity, authentication, authorization, service state, application state, and finally orchestration.
- Treat infrastructure destruction and restoration as first-class lifecycle operations, not afterthoughts.
- Design optional Terraform resources so their dependent resources are optional as well.
- Prefer dynamic discovery and cloud-native management mechanisms over hard-coded hosts and manually distributed credentials.
- Use health checks, readiness signals, and rollout verification instead of assuming that a started process or accepted manifest is healthy.
- Keep production artifacts immutable and traceable from Git commit through container registry to deployment.
- Use short-lived federated credentials and least-privilege roles for CI/CD.
- Design rollback before a deployment fails, and restore the exact previously running release rather than relying on mutable tags.
- Combine infrastructure monitoring with workload-level observability.
- Include cost control, security, validation, documentation, and evidence as part of the engineering lifecycle itself.
